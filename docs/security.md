# セキュリティ設計と既知の制約

このドキュメントは、Jimoto GPU Pod の脅威モデル、現在の防御、既知の制約をまとめたものです。
脆弱性の報告方法は [SECURITY.md](../SECURITY.md) を参照してください。

> 最終更新: 2026-10-31 / 対象: main ブランチ（0.1.0）

## 1. 前提となる信頼モデル

| 登場人物 | 信頼度 | 前提 |
| --- | --- | --- |
| 利用者 | 低 | コンテナ内では何でも実行できる。他者・ホストへの影響は防ぐ |
| 提供者 | 中 | 自分の PC の管理者。Docker ソケット操作 = ホスト root 相当を許容する |
| 中央管理者 | 高 | サーバーと秘密鍵を管理する。運用手順を守る |
| ネットワーク攻撃者 | 低 | 公開ポートへのスキャン・総当たり・改ざんを試みる |

**提供者を完全には信頼しません。** 承認済みテンプレート以外を起動させない、利用者の公開鍵だけで SSH を認証する、
中継は割り当てたポートだけを転送する、といった制約で利用者を守ります。
一方で、提供者のホスト自体の安全（Docker デーモン、GPU ドライバー、OS）は提供者の責任範囲です。

## 2. 資産

| 資産 | 保管場所 | 漏えい時の影響 |
| --- | --- | --- |
| 利用者のアカウント / セッション | 中央の SQLite | なりすまし、貸出の乗っ取り |
| 提供 PC の機材キー | `node-*.secret.json`（提供 PC 上） | 提供 PC のなりすまし、貸出操作 |
| 中継の SSH ホスト鍵 | `$GPUPOD_CONTROL_STATE/relay-host-key` | 中継への MITM |
| 利用者の SSH 公開鍵 | 中央の DB | 単体では悪用しにくいが個人特定につながる |
| 作業データ（/workspace） | 提供 PC の Docker ボリューム | 利用者の研究成果・個人情報 |
| Discord Client Secret | 中央の環境変数 | OAuth なりすまし |

## 3. 境界と防御

### 3.1 認証・セッション（中央）

- パスワードは PBKDF2 でハッシュ化して保存します（平文・可逆保存なし）。
- Discord OAuth2（`identify email guilds`）でログインします。**指定 Discord サーバーへの参加が必須**で、
  未参加なら参加手順を表示します。`GPUPOD_DISCORD_ALLOWED_ROLE_IDS` でロール制限もできます。
- セッションはサーバー側に保存し、Cookie は `Secure` / `HttpOnly` / `SameSite` を設定します
  （`GPUPOD_INSECURE_HTTP=1` のときだけ `Secure` を外します）。
- 状態変更の POST は CSRF トークンと `Origin` 検査（`GPUPOD_CSRF_ORIGINS`）を通します。
- `Host` ヘッダーは `GPUPOD_ALLOWED_HOSTS` で制限します。
- ログアウト、パスワード変更、OAuth 連携解除を提供します。

### 3.2 提供 PC の認証

- 登録時に 48 バイトのランダムな機材キーを発行し、DB には SHA-256 ダイジェストだけを保存します。
- 認証は Bearer トークンで行い、比較はタイミング差が出にくい方法で行います。
- キーのローテーションは prepare / commit の 2 段階で、応答喪失時も同じ候補キーで再試行できます。
- 中央はハートビートが失効した提供 PC をオフラインとして扱います。

### 3.3 貸出の境界

- 利用できるのは**中央で有効な承認済みテンプレートだけ**です。任意のイメージ、ホストのマウント、
  Docker オプションは指定できません。
- 中央と提供 PC のカタログ指紋が一致したテンプレートのみ貸し出します。
- コンテナはテンプレートごとに固定のポート（22 / 8888 / 6006 / 8080）だけを公開します。
- SSH は利用者が登録した公開鍵でのみ認証し、ユーザーは `pod`、作業場所は `/workspace` です。
- RAM・ディスクは提供枠から事前に予約し、合計が枠を超える要求は拒否します。
- 返却時はコンテナと作業ボリュームを削除します。提供 PC がオフラインの間は予約を維持します。

### 3.4 中央中継

- 提供 PC は中央へ**外向き**に接続し、中央の SSH 中継（19000/TCP）へ逆向きのポート転送を作ります。
  提供 PC 側に公開ポートは不要です。
- 中継は、その提供 PC に割り当てた実行中貸出のポートだけを許可します。
  SSH シェルや任意宛先への接続は受け付けません。
- 中継ホスト鍵は提供 PC の設定に固定（`relay_host_key`）し、known_hosts に依存しません。
- 割当ポートは DB で重複を防ぎ、19001〜19999 の範囲から選びます。

### 3.5 コンテナ分離とホスト

- 既定は runc。gVisor（runsc）を選べる構成では、カーネル攻撃面を減らせます
  （`gpupod-tools prepare-runtime` で固定版を取得・検証）。
- GPU はデバイスとしてコンテナへ渡します。GPU ドライバーとファームウェアの脆弱性は分離の対象外です。
- 提供 PC の Docker ソケット操作はホスト root 相当です。提供者はその前提を理解して参加してください。

### 3.6 更新の完全性

- エージェントの更新は ed25519 署名 + SHA-256 の簡易 TUF 風メタデータ（root / targets / snapshot / timestamp）で
  検証します。Python 版の TUF リポジトリとは互換性がありません。
- 署名鍵は中央のオフライン領域に置き、リポジトリへコミットしない運用を前提にしています。

### 3.7 情報の露出を抑える設計

- 公開 LP には GPU 名・ベンダー・VRAM・提供者表示名・空き状態だけを出し、IP・内部 ID・パスは出しません。
- `gpupod-tools support-bundle` はトークン・鍵・ホームパスを伏字にしてからアーカイブします（自動送信なし）。
- 回線測定 API にはクールダウン（300 秒）を設けています。

## 4. 既知の制約（設計上の割り切り）

1. **コンテナ分離はカーネルを共有します。** gVisor を使わない場合、カーネル脆弱性による脱出リスクは残ります。
   信頼できない利用者を長期間受け入れる用途では gVisor を推奨します。
2. **GPU は排他制御が限定的です。** GPU の割当はアプリケーション層で管理しますが、デバイス自体の分離は
   ドライバー依存です。VRAM の強制クォータは保証しません。
3. **提供者のホストは守れません。** Docker ソケット、GPU ドライバー、物理アクセスは提供者の責任です。
4. **中央は単一障害点です。** 冗長化はなく、再起動で中継も切れます（イベント中の再起動は避けます）。
5. **レート制限・WAF はアプリにありません。** 公開時は nginx の `limit_req` や fail2ban を併用してください。
6. **監査ログは journald のみです。** 誰がいつ何を借りたかの長期保存や SIEM 連携は未実装です。
7. **Discord への依存があります。** Discord 障害時は OAuth ログインが使えません（パスワードログインは利用可能）。
8. **課金・返金がありません。** すべて無料のため、不正利用の抑止はコミュニティの規範と受付 ON/OFF に依存します。
9. **docker-compose のデモは本番向けではありません。** HTTP、Docker ソケットのマウント、
   ホストネットワークを使います。ローカル検証以外で公開しないでください。

## 5. 既知の依存脆弱性

`cargo audit` を PR と週次で実行しています（`.github/workflows/audit.yml`）。
以下の勧告は `.cargo/audit.toml` で一時的に除外し、追跡しています。**解消したら除外を削除してください。**

| 勧告 | クレート | 深刻度 | 影響 | 状態 |
| --- | --- | --- | --- | --- |
| RUSTSEC-2026-0154 | russh 0.54.5 | 7.5 high | SSH 実装の 32bit 割当。中継・エージェントが影響 | 未修正。russh >= 0.60.3 への更新が必要 |
| RUSTSEC-2026-0153 | russh-cryptovec 0.52.0 | 7.5 high | 同上 | 未修正。russh 更新で解消見込み |
| RUSTSEC-2023-0071 | rsa 0.9.10 | 5.9 medium | Marvin Attack（RSA 復号のタイミング） | 修正版なし。RSA 秘密鍵をサーバーで扱わない前提で影響は限定的 |
| RUSTSEC-2026-0387 | crypto-bigint 0.5.5 | 未評価 | 定数時間を意図した演算のタイミング差 | rsa 経由。rsa 更新待ち |
| RUSTSEC-2026-0374 | basic-toml 0.1.10 | 警告 | メンテナンス終了 | ビルド時のみ。実行時影響なし |

緩和策:

- 中継は認証済みの提供 PC からの接続だけを受け、転送先も割当ポートに限定しています。
- 中央と提供 PC の間は TLS 前提です。提供 PC は外向き接続のみで、待ち受けポートを持ちません。
- 依存更新は Dependabot と週次監査で検知します。

## 6. 運用で守ること

- `GPUPOD_DISCORD_CLIENT_SECRET` と `node-*.secret.json` は 0600 で保存し、リポジトリ・Issue・チャットへ貼らない。
- `.control-state/`（DB・ホスト鍵・セッション鍵）はバックアップも含めて秘密情報として扱う。
- 中央の 8000/TCP は公開しない（nginx 経由のみ）。19000〜19999 は必要な範囲だけ開放する。
- `GPUPOD_INSECURE_HTTP=1` はローカル検証だけ。本番では TLS と `GPUPOD_TRUST_PROXY` を使う。
- イベント後は受付を OFF にし、残存コンテナ・ボリュームを確認する（[operations.md](operations.md)）。
